# 「応答なし」/ UIフリーズ対策 (2026-08-19)

第1ラウンド: 低スペックPC。第2ラウンド: ファイルサーバ上のセッション（本書後半）。

`docs/UI_PERFORMANCE_IMPROVEMENT_CANDIDATES_20260606.md` の続編。前者が候補の
列挙だったのに対し、本書は「低スペックPCで起動時・セッションを開いた時に
Windows が『応答なし』を出す」という具体的な報告に対して実施した対策の記録。

## 診断

UI スレッドが 5 秒以上メッセージポンプを回さないと Windows は「応答なし」を
出す。実測で以下が判明した。

1. **セッションを開く処理が1フレームで全部走っていた**（最大要因）。
   `tick_project_open()` は「Opening session...」を1フレーム描いた直後に、約
   1000 行の復元処理を次の1フレームで完走していた。内訳:
   - パス修復が**参照ファイル全件に `exists()`**
   - リスト再構築が**全行に `is_file()`**
   - virtual item / cached edit / tab sidecar / preview overlay の
     **件数分の decode + resample + 波形ピラミッド生成**
   - 旧リストのインライン解放
2. **list の sort / filter が 5 万件まで完全同期**だった。開発機基準の固定
   閾値で、2コア機では数秒。
3. **フレーム全体の予算が無かった**。個別予算を持つ drain はあったが合計を
   抑えるものが無く、複数が同時に着地すると加算された。
4. **アイドル時も 80ms ごとに再描画し続けていた**。ウィンドウが完全に眠る
   ことが無く、弱い iGPU では常時 CPU を消費してワーカーと奪い合っていた。
5. セッションを閉じる時の autosave、起動時のシステムフォント読み込み、行の
   存在確認が同期のまま残っていた。

## 対策

### 1. マシン性能ティア (`src/app/perf_profile.rs`)

コア数から Low / Normal / High を決め、**UI スレッドの予算をすべてここから
導出**する。固定定数をやめたのが要点。

| | Low (≦2コア) | Normal | High (≧8コア) |
|---|---|---|---|
| フレーム予算 | 4ms | 8ms | 12ms |
| sort/filter 同期閾値 | 2,000 | 20,000 | 50,000 |
| list job スライス | 1.0ms | 2.0ms | 3.0ms |
| 復元同時実行 | 1 | cores-1 (≦3) | cores-1 (≦4) |
| meta pool | 1 | cores-1 (≦4) | cores-1 (≦6) |

- フレームが継続して遅い場合は自動で1段下げる。**戻しはしない**（数フレーム
  速いだけで方針が往復すると編集中に挙動が揺れるため）。
- Settings > Performance > Responsiveness で手動固定できる（`perf_tier` として
  prefs に保存）。VM・リモートデスクトップ・他が重い環境など、コア数から
  読めないケース用。

### 2. フレーム全体の予算 (`src/app/frame_budget.rs`)

`run_frame_pre_ui` の約60個の drain のうち、**ユーザーが同期的に待っていない
もの**（meta、metadata summary、spectrogram、viewport、external load、
inspection、duplicate、transcript/music AI、folder watch、LUFS recalc）を
共有デッドラインでガードする。予算切れなら次フレームに持ち越し、repaint を
要求する。

**ガードしないもの**（遅延に直結する）: 再生同期、audio device 復帰、IPC、
入力・ショートカット、editor decode/apply の完了反映、export。

無予算だった drain にも上限を入れた: editor feature 解析と editor 波形キャッシュ
（1件ごとに全チャンネル波形＋ピラミッドを複製する）は2件/フレーム、folder
watch イベントは512件/フレーム。

### 3. セッション読み込みの段階化 (`src/app/session_ops.rs`)

`open_project_file` を3段階に分けた。

1. **Parse**（ワーカー）— 読み込み・デシリアライズ・バージョン確認・パス修復。
   app state に触らないので丸ごとワーカーへ出せる。ついでに**行ごとの存在
   マップ**もここで作り、リスト再構築側の `is_file()` を消した。
2. **Decode**（ワーカー、同時実行数はティア依存）— sidecar と virtual source
   を全部先に decode する。各呼び出し箇所は元のインライン decode を
   フォールバックとして残してあるので、収集漏れ・decode 失敗・同一参照の
   2回目は従来どおりの挙動になる。バッファは clone ではなく take するので
   ピークメモリは増えない。
3. **Apply**（UI スレッド）— 復元済みの音声を引き当てながら state に反映。

- `open_project_file` は CLI / kittest / 単体テスト用にブロッキングのまま残置。
- 世代番号を持ち、復元中に別セッションを開いたら旧ワーカーの結果は破棄する。
- トップバーにフェーズ名と Cancel を出す。
- 復元中は**読み取り専用**: スクロール・選択・再生は可、保存と apply は拒否。

### 4. アイドル時に眠る (`src/app/frame_ops.rs`)

やることが本当に何も無いときは `request_repaint_after` を呼ばない。ポーリング
していたチャンネルのうち、外部から入ってくる2つは**スレッド側から起こす**
方式に変えた（`src/ui_wake.rs`）:

- IPC listener（2つ目のインスタンスがファイルを転送してくる）
- folder watch

出力ストリームがある間だけ 1Hz のハートビートを残す（デバイス抜けの検出は
このループが回らないと進まないため）。再生中は従来どおり 16ms。

### 5. 残りの同期 I/O

- **Session Close の autosave**: 編集タブ・virtual item ごとに WAV を同期書き
  出ししていた。既存の非同期保存に載せ替え、書き終わってからセッションを
  破棄する。保存に失敗した場合はセッションを開いたままにする（従来どおり）。
- **システムフォント**: 起動時に数MBの CJK フォントを最初のフレームの前に
  読んでいた。埋め込みの NotoSansJP だけでウィンドウを出し、システムフォント
  はワーカーで読んで差し替える。
- **行の存在確認**: TTL 2秒だが可視行が一斉に期限切れするため、1フレーム
  8件までに制限した。

### 6. 長フレームの記録 (`src/app/frame_ops.rs`, `debug_ops.rs`)

250ms を超えたフレームを、そのとき動いていたもの（session-open / scan / sort /
editor-decode / meta / spectrogram / 予算持ち越しの有無）とセットで直近16件
記録し、Debug ウィンドウ（F12）に現在のティアと並べて表示する。

**「自分の環境で固まる」という報告を、再現やプロファイラ無しで切り分ける**
ための情報源。報告を受けたら F12 の `long_frames` と `perf_tier` を見る。

## 検証

- `cargo test --lib` / `cargo test --features kittest`
- 新規テスト:
  - `perf_profile`: ティア判定、ワーカー数がコア数を超えないこと、降格が
    片方向であること、pin したティアが降格しないこと、prefs 往復
  - `frame_budget`: 予算切れのラッチ、リセット、持ち越し件数
  - `session_ops`: 段階復元と一括復元の結果一致、prefetch 有無での一致、
    存在確認がワーカーに移っても欠損ファイルが検出されること、キャンセル
- 手動:
  1. 数百ファイル＋編集タブ複数の `.nwsess` を `--open-session` で起動し、
     復元中にウィンドウ移動・スクロール・Cancel ができること
  2. `--dummy-list 30000` でソート/検索/スクロールし、F12 の frame peak を比較
  3. 無操作時のタスクマネージャ CPU がほぼ 0 になること
  4. Settings で Low 固定にして 1〜3 を再実行

# 第2ラウンド: ファイルサーバ上のセッション

## 追加の要望

「読み込みに時間のかかる時（ファイルサーバのセッションを開く時）でも、応答なしに
なったり固まったりしにくくしてほしい」。

## ローカル遅延との違い

第1ラウンドは「重い処理を UI スレッドから外す」だった。ネットワークでは前提が
変わる。**SMB では `is_file()` 1回が数十秒ブロックし得る**（サーバ無応答、VPN
切断、スリープ復帰直後）。ローカルなら無視できる 1 回の stat が、そのまま
「応答なし」になる。したがって原則はひとつ:

> **UI スレッドからファイルシステムを一切叩かない。**

「1フレーム8件まで」のような予算では足りない。8件でも無応答共有なら 8×数十秒。
**ゼロにする**必要がある。

## 対策

### A. パス状態サービス (`src/app/path_status.rs`)

低優先ワーカー1本＋キャッシュ。UI はキャッシュを読むだけで、絶対にブロックしない。

- 未確定は `PathStatus::Unknown` を返し、**通常表示**（`treat_as_present()`）。
  ファイルサーバでは大半が存在するので、逆にすると開くたびにリストの大半が
  一瞬グレーになる。
- TTL はリモート30秒／ローカル2秒。共有への probe は高価で、しかも「欠損」の
  大半は削除ではなくリンク断なので、2秒ごとに聞き直す意味がない。
- 結果は既存の `deferrable!` drain で取り込み、ワーカーは `ui_wake` で起こす。

置き換えた呼び出し:

| 場所 | 以前 |
|---|---|
| リストの行 | 8 stat/フレーム（第1ラウンドの上限）|
| Metadata Inspector の source 解決 | **毎フレーム1 stat、上限なし** |
| 行の右クリックメニュー | **選択件数分 × 毎フレーム**（500件選択なら500 stat/フレーム）|

### B. Apply 段階から I/O と重い CPU を追い出す

- **残りの stat を Parse ワーカーへ**: tab / virtual source / managed asset /
  external source の存在を `ParsedSession::other_exists` にまとめる。Parse
  ワーカーはパス修復で同じパスを既に stat しているので追加コストはほぼ無い。
  マップに無いパスは「存在する」扱い（従来の挙動を保つ）。
- **resample と波形キャッシュ生成を Decode ワーカーへ**: 編集タブになる sidecar は
  ワーカー側で出力レートへ正規化し、波形＋ピラミッドまで作って渡す
  (`PreparedSidecar`)。Apply 段階は代入するだけ。
- 結果として **Apply 段階のファイルシステム呼び出しはゼロ**。

### C. 進捗と遅延警告

`Decoding session audio 12/48 — kick_01.wav` ＋バー。10秒間 1件も完了しなければ
`Waiting on kick_01.wav` に切り替える（in-flight の最古＝共有が返してこないもの）。
decode 失敗も進捗として数える（欠損だらけのセッションが 0/n のまま止まって
見えないように）。

### D. 背景処理がリンクを食い潰さないようにする

- **folder watch**: 固定3秒 → **直前の walk 所要時間の4倍**（下限は設定値、上限
  5分）。共有で1回の walk が30秒かかると、従来は実質ずっと walk し続けていた。
  セッション読み込み中は完全に suspend する。
- **meta pool / prefetch**: ルートがリモートなら worker 2本、予算1/4。読み手を
  増やしても共有は速くならず、ユーザーが開いたファイルが後ろに並ぶだけ。
- リモート判定は既存の `audio_io::is_remote_file_path`（UNC / `GetDriveTypeW`）を
  `pub` にして再利用。ルートが無いセッションでは先頭アイテムのパスで判定する。

## 残した UI スレッドの fs 呼び出し（意図的）

- `ui/tools.rs:26` — アプリ自身の設定ファイルパス。共有には載らない。
  （第3ラウンドで 1 秒キャッシュにした。共有には載らないが、**毎フレーム**
  叩いてよい理由にはならない。）
- `ui/metadata_inspector.rs:2170` — 保存ダイアログでユーザーがパスを選んだ直後の
  1回。ダイアログ自体が既にブロックしている。

## 検証（第2ラウンド）

**新規テスト**
- `path_status`: UI 経路が絶対にブロックしないこと、結果反映で Present/Missing に
  なること、毎フレーム再描画される行が1回しかキューされないこと、preload が
  probe を省くこと、リモート/ローカルで TTL が変わること、clear の後始末。
- `session_ops`: 欠損した tab source が Parse ワーカーで解決されること、
  prepared sidecar が波形ピラミッドまで持っていること、進捗が件数で報告される
  こと（失敗も含む）、ラベルがファイル名であること、停滞時に in-flight 最古を
  名指しすること。
- `watch`: 速い walk では設定間隔、遅い walk では比例して延び、上限で頭打ちに
  なること。
- `perf_profile`: リモート時に meta worker / restore 並列度 / 予算がすべて下がり、
  それでも 1 は下回らないこと。ティア変更でリモート判定が失われないこと。

**手動（ファイルサーバ相当）— この環境では未実施**
1. 遅延を入れた SMB/NFS マウント、または Windows 実機の共有を用意する。
2. 数百ファイル＋編集タブ複数のセッションを共有上に置き、`--open-session` で
   起動 → 復元中にウィンドウ移動・リストスクロール・Cancel ができること。
3. 読み込み中にサーバを落とす → ウィンドウが応答し続け、`Waiting on ...` が
   出ること。
4. F12 の `long_frames` に 250ms 超が出ないこと。
5. 共有上のフォルダを開いて放置 → walk が連続していないこと。

## 積み残し（第2ラウンド）

- Apply 段階のフレームまたぎスライスは未実装。stat と O(n) パスを追い出した結果、
  残りは代入と索引更新が主体になったため優先度を下げた。virtual item が非常に
  多いセッションでは `AudioBuffer::from_channels(channels.clone())` が効くので、
  そこが問題になったら着手する。
- `build_meta_from_audio` は Apply 段階に残っている（1回の min/max/RMS パスで、
  ピラミッド生成より大幅に軽い）。

## 積み残し（第1ラウンド）

- Apply 段階の resample・`build_meta_from_audio`・`build_editor_waveform_cache`
  は UI スレッドに残っている。decode を外に出したことで支配的ではなくなったが、
  極端に長いセッションではここをフレームまたぎでスライスする余地がある。
- リスト構築自体（`reset_list_from_project` の行生成ループ）はまだ1フレーム。
  存在確認を外したので大幅に軽くなったが、数十万件では分割の価値がある。

# 第3ラウンド: 「固まる」の残り二種

第1・第2ラウンドは**遅い**（フレームが伸びる）への対策だった。第3ラウンドは
**戻ってこない**（状態が解除されない／毎フレームの仕事が選択範囲に比例する）の
二種類で、どちらもフレーム予算では救えない。

## X. 応答しないジョブが「終われないアプリ」になっていた

### 症状

モーダルオーバーレイ（`loading_ops::ui_busy_overlay`）は全入力を食う。これを出す
5 つの状態 — export / CSV export / session save / clipboard prep / bulk resample —
のうち channel を持つ 4 つは、**ワーカーからのメッセージだけ**で解除される。
受信側は `Err(_) => None`、つまり「まだ来ていない」と「もう二度と来ない」を
同じ扱いにしていた。

ワーカーが panic するか結果を送らず終了すると送信端が落ち、`try_recv` は以後
ずっと `Disconnected` を返す。その結果:

1. オーバーレイが**永久に残る**（キャンセルボタンは bulk resample にしか無い）。
2. 終了ダイアログは通常の `egui::Window`（Order::Middle）なので、
   `Order::Foreground` のオーバーレイの**下**に描かれ、クリックできない。
   → **アプリを正常終了する手段が無い**。未保存の編集はプロセス kill と一緒に消える。
3. `frame_ops` の repaint 判定はこれらの状態を見ているので、**50ms / 60fps の
   再描画が永久に続く**。何もしていないのに 1 コアを回し続ける。

### 対策

- `loading_ops::poll_job` / `JobPoll<T>`（`Waiting` / `Ready` / `Gone`）。
  **「まだ」と「もう来ない」を型で分ける**のが核心で、`Gone` を持つ以上、
  呼び出し側は無視できない。`playback_fx` の drain が元から持っていた規則を
  全ジョブに広げた形。
- 4 つの drain に `Gone` の腕を足した。状態を解除し、何が起きたかをトーストで
  言う。保存は「**セッションは書かれていない**」と明示する（tmp → atomic replace
  なのでディスク上の元ファイルは無傷）。export は `saving_*` の帳簿も一緒に
  片付ける — 残すと**次のエクスポートの結果に適用されてしまう**。
- **生きたまま止まったジョブ**（無応答になった共有ドライブ）には検出手段が無い
  ので、30 秒（`BUSY_OVERLAY_STALL_SECS`）でオーバーレイに「Stop waiting」を出す。
  ジョブは止めない・止められないことを明示し、**ウィンドウだけ返す**。
  全状態が解除されたらこのフラグは戻る（一度の停滞で以後の保存が非モーダルに
  なってしまわないため）。
- 終了要求が出ている間はオーバーレイを描かない。**どんなジョブより「閉じたい」が
  優先**で、答えの返らないジョブが終われない理由になってはいけない。
- CSV export は channel を持たず「pending が空になったら完了」なので、
  measure できない行があると**キューに戻し続けて無限ループ**していた。
  4 回で諦め、空欄で書き、**何行落としたかをトーストで出す**。

## Y. メニューを開いている間の毎フレーム O(選択数)

### 症状

メニューの中身は**開いている間ずっと毎フレーム実行される**。そこに選択範囲ぶんの
仕事が入っていた。

| 場所 | 毎フレームやっていたこと |
|---|---|
| List メニュー | `selected_paths()`（全選択パスの clone + ソート）を **4 回** |
| 行の右クリック | 同 2 回 ＋ **タグ定義数 × 選択行数**の照会 ＋ 全選択の変換可否走査 |
| どちらも | Paste 判定で **OS クリップボードを毎フレーム 2 回開く** |
| Command Palette | 全選択の clone ＋ 設定パス解決（**`create_dir_all` を毎フレーム**）＋ stat |

10 万行を Ctrl+A した状態で右クリックすると、それだけでアプリが止まる。
クリップボードは Windows では**他アプリと取り合うグローバルなロック**なので、
秒 120 回開くのは他のアプリのコピペを壊しうる。

### 対策

- 「何行あるか」「2 行以上か」は上限付きカウント（`selection_has_at_least`）。
  選択がいくら大きくても定数時間で答える。
- ステータス共有 / タグ状態 / 変換可否 / 未保存編集 / rename 可否 / transcript
  対象数は、**1 回のパスにまとめて 250ms キャッシュ**（`SelectionMenuSummary`）。
  メニューが開いている間に選択は変わらないので、キャッシュしても答えは同じ。
  メニュー内で選択のラベルを変えた時だけ明示的に破棄する。
- パスの実体（`selected_paths()`）は**クリックされた項目の中でだけ**作る。
- Paste 判定と Command Palette の設定パスも同じ規則でキャッシュ（250ms / 1秒）。

### 規則として残したもの（`AGENTS.md`）

> メニューの中に、選択数やリスト長に比例する仕事を置かない。
> `selection_menu_summary()` を読み、パスはクリックされた腕の中で作る。

## 検証（第3ラウンド）

`tests/stability_regressions.rs`（10 件）。

- 保存 / エクスポート / クリップボードの**ワーカーが死んだ状態を注入**し、
  次のフレームで状態が解除され、オーバーレイが消え、トーストが出ること。
- ジョブが**生きたまま**ブロックしている間に終了ダイアログの Cancel が
  **クリックできる**こと（オーバーレイが入力を食っていれば落ちる）。
- 30 秒超のジョブに「Stop waiting」が出て、押すとオーバーレイだけ解除され、
  **ジョブは走り続けている**こと。その後の新しいジョブは再びモーダルになること。
- 測れない行がある CSV export が pending を空にして終わり、件数を報告すること。
- List メニューを開いたまま 10 フレーム進めても、`selected_paths()` の構築と
  選択パスの走査が**増えない**こと（カウンタで観測。修正前の実装を戻すと落ちる）。
- 250ms 窓の中で 100 回聞いてもクリップボードの実測は 1 回であること。

## 積み残し（第3ラウンド）

- `begin_export_list_csv` は開始時に**全行 `is_file()`** を UI スレッドで叩く。
  ユーザー操作 1 回きりなので毎フレームではないが、共有上の 50 万行では
  ここが数分になる。`path_status` に寄せるのが筋（既存の「存在は背景サービスに
  聞く」規則どおり）だが、「まだ probe していない行は present 扱い」の意味が
  変わるので、CSV の出力内容への影響を確認してからにする。
- ジョブ以外の `try_recv` 全 57 箇所を見た結果、editor decode / preview /
  plugin / recording / music AI / effect graph / auto trim / loop detect は
  いずれも `Disconnected` を正しく扱っていた。穴はモーダル 4 つに集中していた。
- 「生きたまま止まった」の検出は 30 秒の一律しきい値。ジョブごとの進捗を見て
  出し分ける余地はあるが、進捗の無いジョブ（clipboard prep）があるので一律にした。
